# llm-pdf-to-pdf-translator

LLM-based PDF-to-PDF translator for text-first technical documents with layout preservation.

This repository was used in practice for translating technical documentation, especially structured PDF files such as SDS / MSDS / GHS documents, manuals, forms, and other layout-sensitive materials.

## Что это

Этот проект использовался для перевода технической документации и переводит PDF-документы из одного языка в другой, собирая новый PDF с попыткой сохранить исходную вёрстку:

- заголовки
- абзацы
- табличные блоки
- служебные коды и числовые значения

Основной сценарий использования:

- SDS / MSDS / GHS-документы
- технические PDF с извлекаемым текстом
- формы и структурированные документы
- документы, где важно получить именно `PDF -> PDF`, а не просто текстовый перевод

Проект не является системой перевода картинок или полноценным OCR-конвейером. Он лучше всего работает там, где в PDF уже есть нормальный текстовый слой и координаты блоков.

## Что делает пайплайн

1. Скрипт читает исходный PDF и извлекает текстовые блоки и их координаты.
2. Блоки классифицируются: заголовки, абзацы, табличные ячейки, коды, числовые значения.
3. То, что не нужно переводить, сохраняется как есть.
4. Переводимые блоки проходят через локальные правила, словарь и кэш.
5. Только новые или нерешённые фрагменты отправляются в LLM через OpenAI API.
6. Новый текст укладывается обратно в PDF в исходные зоны.
7. На выходе получается новый PDF с переведённым текстом.

## Что сохраняется без перевода

Скрипт старается не трогать:

- H/P/EUH-коды
- CAS-номера
- проценты
- температуры
- короткие идентификаторы
- часть табличных и химических обозначений

Это важно для технических и нормативных документов, где прямой перевод всего подряд ломает смысл.

## Кэш и артефакты

Проект использует кэш переводов и служебные логи.

- Кэш позволяет не переводить одинаковые блоки повторно.
- Логи помогают понять, где перевод не поместился, где был fallback и где надо вручную доработать стратегию.
- Повторный рендер может использовать уже накопленный кэш без повторных затрат на API.

Служебные данные пишутся в `PDF/_artifacts/`.

## Быстрый старт

### 1. Установить зависимости

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Настроить API

Создай `.env` рядом с `.env.example`:

```env
OPENAI_API_KEY=your_openai_api_key
OPENAI_MODEL=gpt-5.4-mini
```

В проекте использовался OpenAI API / ChatGPT API-ключ с явно указанной моделью через переменную `OPENAI_MODEL`. Модель можно менять в `.env` или через аргументы запуска.

### 3. Положить исходные файлы

Скопируй исходные PDF в `GHS_MSDS/`.

### 4. Запустить перевод

Одиночный файл:

```bash
python scripts/translate_pdf_layout.py \
  GHS_MSDS/example.pdf \
  PDF/translated/example_ru.pdf \
  --artifact-dir PDF/_artifacts \
  --model gpt-5.4-mini
```

Пакетная обработка папки:

```bash
python scripts/batch_translate_msds.py \
  --input-dir GHS_MSDS \
  --output-dir PDF/translated \
  --artifact-dir PDF/_artifacts \
  --model gpt-5.4-mini \
  --skip-existing
```

Или через bash-раннер:

```bash
bash run_remaining_translations.sh gpt-5.4-mini
```

## Полезные утилиты

- `run_remaining_translations.sh` — пакетный запуск перевода по входной папке
- `rerender_all.sh` — повторный рендер из кэша без повторного API-вызова
- `compress_translated.sh` — сжатие готовых PDF через Ghostscript
- `scripts/fix_identity_cache.py` — чистка плохих identity-кэшей
- `scripts/find_and_retry_untranslated.py` — поиск и повтор проблемных блоков
- `scripts/cache_quality_fix.py` — дополнительная чистка кэшей
- `scripts/report_translation_quality.py` — отчёт по качеству и проблемам
- `scripts/export_translation_html.py` — экспорт перевода в HTML для просмотра

## Ограничения

Проект не гарантирует идеальную вёрстку для любого PDF.

Проблемные случаи:

- очень плотные таблицы
- нестандартные шрифты
- слишком узкие блоки
- PDF без нормального текстового слоя
- документы, где текст фактически лежит в виде картинок
- документы с очень длинным переводом по сравнению с исходным английским

Именно поэтому каждый PDF стоит проверять после рендера.

## Где могут потребоваться ручные правки

Каждый PDF уникален. На некоторых файлах:

- текст может не влезать в блок
- строки могут переноситься хуже, чем в оригинале
- таблица может потребовать отдельной логики
- заголовок может оказаться слишком длинным
- блок может нуждаться в отдельных правилах перевода или исключениях

Обычно такие случаи решаются:

- правкой эвристик в `scripts/translate_pdf_layout.py`
- правкой правил и глоссария в `msds_translation_engine.py`
- чисткой кэша и повторным рендером
- локальной доработкой конкретного класса документов

## Использование вместе с Codex или Claude

Этот репозиторий хорошо подходит для работы в связке с агентами вроде Codex или Claude.

Их можно просить:

- анализировать проблемный PDF-результат
- находить, почему текст не помещается
- предлагать правки эвристик рендера
- чистить кэши и повторно собирать результат
- улучшать классификацию блоков
- адаптировать пайплайн под новый тип документов
- писать дополнительные отчёты и утилиты

Практический сценарий такой:

1. Положить исходный PDF в `GHS_MSDS/`.
2. Запустить перевод.
3. Проверить результат в `PDF/translated/`.
4. Если вёрстка поплыла, дать агенту этот репозиторий и попросить проанализировать конкретный кейс.
5. После правок повторить рендер.

## Безопасность

- Не коммить `.env`.
- Не публикуй реальные API-ключи.
- Если ключ когда-либо был записан в репозиторий или архив проекта, перевыпусти его.
- Для публичного репозитория лучше не хранить внутри реальные входные PDF, результаты перевода и служебные логи.

## Для какого типа документов проект подходит лучше всего

Лучше всего:

- технические PDF с извлекаемым текстом
- SDS/MSDS/GHS
- инструкции
- регламентные документы
- формы с таблицами и короткими блоками

Хуже всего:

- сканы без текстового слоя
- тяжёлые дизайнерские брошюры
- документы, где почти всё нарисовано как изображение

## Лицензия и публикация

Перед публикацией входных и выходных PDF проверь права на распространение исходных документов. Сам код можно публиковать отдельно, а реальные рабочие PDF, кэши и результаты лучше держать вне репозитория.
